Clase 8

El Test Plan y el Test Report

Repaso, vemos test plan

  • Smoke testing, regression tests, funcional/ no funcional
  • CRUD = create, read, update, delete - operaciones básicas posibles en una base de datos. en español abmc (alta baja modificacion consulta)
  • tipos de técnicas de diseño de pruebas (partición de equivalencias, análisis de valores limite, tabla de decisiones)
  • severidad y prioridad.
  • test plan (define la estrategia general para asegurar la calidad de la aplicación. su propósito es alinear el equipo de qa y los stakeholders. se genera durante el principio, que se va a testear, cómo. alcance, prioridades, criterios de exito del proceso de testing. se crea el test plan como documento. generalmente creado por el qa con mayor experiencia.) (buscar templates de test plan para ver cómo son)

  • Qué esta por dentro de lo que vamos a testear y que cosas quedan afuera? p. ej. vamos a testear solo en web o también en diversos dispositivos? qué browser usaremos? testeamos Firefox, chrome, explorer?
  • Riesgos y prioridades: qué debemos priorizar x sobre otras, teniendo en cuenta objetivos del producto. puede haber riesgos técnicos, o relacionados con el producto.
  • Estrategia= que tipos y técnicas de testing usaremos
  • Recursos y tiempos. se necesitan a veces ciertas aplicaciones de testing que son pagas. por Ej. si testeamos en mobile necesitamos emular o testear distintos celulares para cubrir distintos modelos tanto android como apple, tiempos realistas pueden ser bajados de arriba (managers, etc), son bastante estimativos en esta instancia.
  • Muy importante el test plan se termina y se comunica al equipo -> entonces el equipo TIENE QUE APORTAR evidencia de que lo leyó. es importante para nosotros como QA para poder prevenir problemas o malentendidos a futuro.

  • objetivo: que tenga una buena calidad de producto.
  • alcance: lo importante que NO formara parte sirve de garantía para asegurar que no se haya testeado si surge alguna duda
  • estrategias: smoke, regression, funcional, no funcional. algo común en algunasaplicaciones no se hace testing funcional. a veces lo hace directamente desarrollador o DevOps y no el QA team.
  • ambientes: vamos a tener ambiente de QA?, de desarrollo? , de staging? cada proyecto puede tener más de un ambiente de cada uno. p ej 3 ambientes de QA. también listamos que herramientas vamos a usar.
  • criterios entrada/ salida: cada proyecto es distinto pero en general. p ej: Criterio de entrada= tener bien escritos criterios de aceptación, ya documentados.
  • Criterio de salida o DONE hace referencia a cuando decimos que una funcionalidad esta testeada y aprobada. puede haber proyectos q admitan algunos bugs no críticos y aun así aprobar el testing. puede haber situaciones donde se acepten ciertos bugs mientras no sean críticos. acá se define eso.

  • Siempre pensar en los riesgos de las actividades de testing porque muchos proyectos subestiman el rol de QA en detrimento de los riesgos. Es rol del QA levantar la mano y avisar "estos son los riesgos que podemos tener si omitimos X cosa".

Vemos un ejemplo en testrail.com (la plantilla en la imagen arriba). deliverables: reportes, test cases, bugs; artifacts hace referencia a documentación.

estos reportes pueden variar mucho dependiendo del proyecto. a veces hay empresas geralemnte internacionales que ya tienen una plantilla de test report. pero nos puede tocar diseñarlo a nosotros.

hay apliaciones que nos permiten generar reportes dentro de la misma aplicacion como Jira, p ejemplo rastrear densidad de defectos, cuantos de todos los tests pasaron (pass rate). reopen rate: de tantos bugs que se resolvieron cuantos volvieron a pasar de vuelta en una nueva sprint (bugs reabridos) slack: plataforma para chatear que se usa en IT. listar l q hiciste en el dia/ semana / sprint para q el q esta cargo sepa como avanzar. siempre es importante de todas formas comunicarse por chats, por mensajes, etc.
