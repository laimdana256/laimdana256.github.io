Implementación, Test Suites, Ejecución y Bugs

Profesora: Agustina Artemis Luna (con aportes de Juli, Vicky/Victoria y otros compañeres)

1. Repaso de la clase anterior

Tipos de testing

  • Funcional: prueba la funcionalidad del producto (ej: comportamiento del login).
  • No funcional: aspectos que no son la funcionalidad en sí (usabilidad, rendimiento, nivel operativo).
  • Caja negra: testing sin conocer la estructura interna del producto (basado en requisitos y funcionalidad, "ir a ciegas").
  • Caja blanca: testing con conocimiento del código y funcionamiento interno de la aplicación.
  • Se mencionaron también testing dinámico y exploratorio.

Operaciones CRUD / ABMC

  • CRUD: Crear, Leer, Actualizar, Eliminar (Create, Read, Update, Delete).
  • ABMC: Alta, Baja, Modificación, Consulta (equivalente en español).

Técnicas de diseño de casos de prueba

  1. Partición equivalente: dividir los datos en grupos que se consideran equivalentes.
  2. Análisis de valores límite: crear pruebas que evalúen el comportamiento en valores mínimos o máximos de un grupo.
    • Ejemplo: campo edad con mínimo 18 y máximo 99 → se prueban 17, 18, 19 (límite inferior) y 98, 99, 100 (límite superior).
  3. Tabla de decisiones: agrupar datos para crear combinaciones de condiciones y acciones (similar a tablas de verdad en lógica).

2. Implementación

Definición: proceso de transformar la planificación o diseño de pruebas en procedimientos accionables (test cases, test scripts).

Incluye:

  • Organizar las pruebas.
  • Preparar los datos de prueba.
  • Configurar los ambientes.
  • Escribir scripts automatizados.

Beneficios de una implementación eficiente:

  • Etapa de ejecución más eficiente y organizada.
  • Ayuda a verificar calidad y funcionalidad con un enfoque estructurado.
  • Permite atacar áreas de riesgo tempranamente, evitando problemas mayores.
  • Facilita un proceso de testing más fácil de mantener.

Ejemplo (campo de edad, min 18 / max 99):

  1. Planificar qué pruebas se harán.
  2. Determinar qué datos usar (en este caso, valores numéricos).
  3. Configurar el ambiente correspondiente.

Ambientes de desarrollo

Ambiente Descripción
Desarrollo (DEV) Donde los desarrolladores implementan y prueban cambios nuevos (constantemente "se rompe").
QA / Staging / Preproducción / Beta Donde el equipo de QA prueba los cambios; copia lo más cercana posible a producción, con datos de prueba.
Producción Ambiente final que usa el cliente/usuario real.
  • El acceso a ambientes bajos (QA, preproducción) suele estar restringido al equipo (a veces mediante VPN), tanto por seguridad como por confidencialidad del código/datos expuestos.
  • A veces se usa staging para mostrarle avances al cliente antes de pasar a producción.

Entorno vs. Ambiente

  • Ambiente: espacio de trabajo con configuraciones y datos según la etapa del desarrollo (DEV, QA, staging, producción).
  • Entorno: conjunto de herramientas y configuraciones locales usadas para probar (hardware, sistema operativo, configuración de red, navegador, etc.).

3. Test Suite

Definición: agrupamiento de tests que corren dentro de una misma ejecución, enfocados en una misma área del sistema o que comparten un objetivo.

Beneficios:

  • Tests más organizados.
  • Ejecuciones más ordenadas.
  • Reportes más claros.

Criterios de agrupamiento:

  • Por área o funcionalidad (ej: suite de "Login", suite de "Playlists").
  • Por prioridad (tests mínimos y necesarios ante cualquier cambio).
  • Por importancia para reglas de negocio y módulos clave.

Ejemplo — Suite de Login:

  • Login con usuario activo.
  • Login con credenciales no válidas.
  • Login con campo de contraseña vacío.
  • Login como usuario administrador.

Ejemplo — Suite de Playlists:

  • Crear nueva playlist.
  • Crear playlist con nombre vacío.
  • Editar portada de playlist existente.
  • Editar nombre de playlist.

Herramientas mencionadas: Trello (agrupación por columnas o etiquetas/tags), Jira, Azure (Test Plan → Test Suite → Test Cases, como "matrioshkas").

Trazabilidad (aporte de Juli): es fundamental poder rastrear de dónde viene un bug — a qué funcionalidad, caso de prueba, tipo de ejecución, navegador y condiciones está asociado. Esto depende de una buena implementación y planificación previas.

Tipos especiales de suites

  • Smoke test: pruebas mínimas y rápidas para asegurar que el sistema no "explotó" tras un cambio; superficiales.
  • Test de regresión: conjunto de pruebas que se ejecutan luego de un cambio para verificar que no se rompió nada más.

4. Ejecución

Definición: proceso de correr las pruebas para verificar la funcionalidad del sistema, identificar defectos y asegurar el cumplimiento de requerimientos.

Actividades dentro de la ejecución:

  • Ejecución de las pruebas.
  • Reporte y seguimiento de errores/defectos/bugs.
  • Mantenimiento y seguimiento de las pruebas.

Es clave para dar feedback sobre el sistema testeado; debe hacerse de forma crítica y sistemática.

5. Error, Defecto y Falla

Concepto Definición Ejemplo
Error Algo humano Error de tipeo en el nombre de un método asociado al botón "Continuar".
Defecto (Bug) Algo del software El botón "Continuar" llama al método equivocado; no sucede nada al hacer clic.
Falla Se manifiesta en la implementación/uso El usuario no puede continuar a la siguiente página.

Bug (definición formal): desperfecto que causa que un componente o sistema falle al realizar su tarea. Sinónimo común: "defecto".

Origen de la palabra "bug": viene de un insecto (bicho) real encontrado en el hardware de una máquina antigua, que causó un desperfecto en los cálculos.

Causas posibles:

  • Variables o datos mal definidos.
  • Métodos o funciones mal declarados/utilizados en el código.
  • Implementación errónea.
  • Aporte de Juli: también puede originarse en un análisis deficiente previo a escribir el caso de prueba (mal entendimiento de la documentación, supuestos no verificados). Por eso es importante preguntar y no asumir al definir el resultado esperado.

Ejemplo curioso (Skyrim): un bug de físicas donde el daño de un golpe dependía de variables mal calculadas según el tipo de superficie, generando comportamientos inesperados (objetos "saliendo volando").

6. Ciclo de vida de un bug

1
Nuevo / Abierto → En progreso → Arreglado (Fixed) → Verificado → Cerrado
2
                                                    ↘ (si sigue fallando) → vuelve a En progreso
  1. Nuevo/Abierto: se encuentra y reporta el bug.
  2. En progreso: un desarrollador lo toma para solucionarlo.
  3. Arreglado/Fixeado: el desarrollador completó el arreglo.
  4. Verificación: QA vuelve a testear.
    • Si el fix funciona → se marca Verificado y se cierra el ticket.
    • Si sigue fallando → vuelve a En progreso (proceso cíclico/iterativo).

Sobre la regresión:

  • Es importante correr pruebas de regresión luego de aplicar cambios, para asegurar que no se rompió otra funcionalidad.
  • Conviene conocer el sistema para enfocar la regresión en las áreas más relacionadas al cambio realizado (no siempre es necesario, ni posible por tiempo, testear todo).
  • Cuanto más completa la regresión, mejor — pero depende del tiempo y prioridades del proyecto.
  • Práctica común: regresión luego de cada nueva versión/release (ej. apps mobile, donde suele haber muchos tickets de usuarios).

7. Reporte de errores (Bug Report)

Estructura recomendada de un reporte

  1. Título: lo más descriptivo posible; debe permitir entender de qué se trata solo con leerlo (evitar títulos genéricos como "error en login").
  2. Precondiciones: pasos/condiciones que deben cumplirse antes de poder reproducir el error.
  3. Datos: información necesaria para reproducir el error (usuario, módulo, ambiente, entorno, versión/build, navegador, sistema operativo, etc.).
  4. Severidad y prioridad (ver sección 8).
  5. Pasos de reproducción: listados en orden (idealmente numerados, escritos en infinitivo: "ingresar", "hacer clic", "completar").
  6. Resultado esperado: comportamiento correcto según especificación/caso de prueba.
  7. Resultado obtenido: comportamiento real observado; en qué difiere de lo esperado.
  8. Evidencia: capturas de pantalla o video que documenten el error (recomendable resaltar visualmente la zona del error, ej. con un recuadro).

Ejemplo trabajado en clase (banco / cambio de género en DNI)

  • Situación real compartida: al cambiar el género en el DNI, la app del banco mostraba error con "masculino" y traía el nombre anterior con "no binarie".
  • Título sugerido: "Error de actualización de datos de nombre y género" (mejor que "error de login", que es demasiado genérico).
  • Precondición: haber realizado el cambio de género/DNI + versión de la app actualizada.
  • Severidad: alta (bloquea el uso operativo de la app a un usuario).
  • Prioridad: alta (afecta a muchos usuarios potencialmente, es urgente).

Ambiente vs. Entorno en el reporte

  • Se recomienda indicar: ambiente (dev/QA/staging/producción), entorno (SO, navegador, dispositivo — Android, iOS, Windows, Linux), versión/build.

Recursos/ejemplos reales mencionados

  • Telegram: tiene una página pública para reportar bugs → bugs.telegram.org.
  • Godot (motor de videojuegos open source): reporta bugs vía GitHub, con estructura similar (título, versión, system information/entorno, descripción, pasos de reproducción, estado del ciclo de vida: abierto/cerrado).

8. Severidad y Prioridad

  • Severidad: qué tan grave es el error a nivel técnico (definida normalmente por el equipo técnico).
  • Prioridad: urgencia con la que se debe resolver el error (impacto en negocio/usuarios).

Combinaciones posibles

Severidad Prioridad Descripción Ejemplos discutidos en clase
Baja Baja Errores menores en funcionalidades poco usadas; impacto mínimo, no afecta componentes clave. Detalle estético menor (ej. un botón con color levemente distinto); link mal alineado en el footer de una sección secundaria.
Baja Alta Bugs pequeños/fáciles de arreglar, pero deben resolverse rápido porque bloquean funcionalidades o detalles clave del negocio. Botón "Continuar" que no redirige por un error de tipeo en el método invocado.
Alta Baja Errores críticos que pueden esperar por ser casos particulares o afectar a pocos usuarios. App bloqueada para un usuario específico (ejemplos reales: Naranja X, sistema de turnos médicos de una ART afectando a un grupo chico de usuarios). Crash en una sección del panel admin usada 2 veces al año.
Alta Alta Errores críticos que afectan funcionalidades clave o a grandes cantidades de usuarios; requieren solución urgente. Bug del DNI/género en la app del banco (afecta a muchos usuarios y genera pérdidas). Backend que crashea al intentar pagar, impidiendo suscripciones.

Nota sobre lo "estético": no siempre es severidad/prioridad baja — si está relacionado a la identidad visual/marca (ej. logo o colores institucionales), puede ser alta prioridad.

Ejemplo real compartido — Mercado Libre:

  • Cambios de logo (manitos/codos durante la pandemia) requirieron campañas de comunicación para que los usuarios no lo confundieran con una estafa (por la asociación marca-confianza).
  • Cambio de colores entre Mercado Libre y Mercado Pago (unificación con el mercado brasileño) generó rechazo de usuarios, incluyendo problemas de fotosensibilidad — mostrando que un cambio "estético" puede tener alta severidad/prioridad si toca la identidad de marca o accesibilidad.

9. Origen de los bugs — causas frecuentes

  1. Errores de desarrolladores en la lógica o implementación (mal entendimiento de la lógica de negocio).
  2. Problemas de comunicación (el equipo funcional no logra explicar bien el módulo, o el mensaje se distorsiona al pasar por muchas personas: cliente → Scrum Master → PO → analista funcional → desarrollador).
  3. Requerimientos poco claros o contradictorios.
  4. Requerimientos que cambian durante el desarrollo.

Recomendación clave: involucrarse tempranamente en el ciclo de desarrollo, preguntar ante dudas, y no asumir — esto previene bugs y mejora la comunicación y el trabajo en equipo (el testing no es solo una tarea individual de ejecutar/escribir casos, sino un trabajo colaborativo).

Consigna: se compartió un formulario web con 15 errores intencionales para encontrar y reportar de forma colaborativa en un tablero de Trello, usando la estructura de reporte vista en clase (título, severidad, prioridad, precondiciones, datos, pasos de reproducción, resultado obtenido/esperado, evidencia).

Errores identificados y feedback de la docente

# Título del error Severidad / Prioridad Feedback / correcciones sugeridas
1 Contraseña visible (no se censura al escribirla) Baja / Alta Bien resuelto en general; agregar navegador y SO; numerar pasos de reproducción; recomendable resaltar visualmente el campo en la evidencia.
2 Error de funcionalidad en términos y condiciones (checkbox no cliqueable, bloquea el registro) Alta / Alta Escribir pasos en infinitivo ("hacer clic", "completar"); aclarar bien resultado esperado vs. obtenido (el campo debería ser cliqueable).
3 No se notifica al usuario al ingresar un mail inválido Alta / Alta Correcto: es crítico porque compromete el propósito del registro (validación de cuenta vía mail).
4 Falla en campos obligatorios (permite registrar sin completar el mail) Alta / Alta Correcto por el mismo motivo que el anterior (dato obligatorio para confirmación).
5 Se acepta el registro sin aceptar previamente términos y condiciones Baja / Alta Bien argumentado: el fix es simple (severidad baja) pero es grave legalmente no exigir la aceptación (prioridad alta). Mejorar redacción de pasos de reproducción (usar infinitivo, separar acciones).
6 Registro muestra información distinta a la cargada (aparenta ser de otro usuario) Inicialmente "urgente/urgente"; tras reproducirlo en vivo se detectó que en realidad el sistema quitaba una letra del apellido y agregaba un dígito al campo teléfono Buen ejemplo de la importancia de reproducir el error para entender exactamente qué está pasando antes de definir severidad/prioridad definitivas — la hipótesis inicial (filtración de datos de otro usuario) resultó ser un bug distinto (corrupción de datos al guardar).
