Clase 6 - Tipos y Técnicas de Testing, Bugs

Tipos y Técnicas de Testing

1. Ejemplo introductorio: reportes de bugs

Ejemplos de reportes que sirven como punto de partida para pensar en testing:

  • "Las personas usuarias no pueden registrarse en la aplicación porque el botón de sign-up no reacciona."
  • "El sistema de reportes no puede procesar datos de 2022."

Se mencionó que este tipo de reportes se suelen gestionar en listas de test (con identificador, si pasó o no pasó, tipo de test), y que herramientas como Jira o Azure DevOps se usan para esto en equipos que trabajan de forma sincrónica.

2. Tipos de testing: funcional vs. no funcional

  • Funcional: verifica las funcionalidades del sistema y su comportamiento (qué hace el sistema).
  • No funcional: verifica requerimientos que no son funcionales (cómo se comporta el sistema: rendimiento, usabilidad, etc.), en lugar de qué hace.

Ejemplos de tipos de testing mencionados

  • System testing
  • API testing (probar que una API funcione correctamente)
  • User Acceptance Testing (UAT)
  • Pruebas de regresión
  • Testing exploratorio
  • Pen testing (seguridad)
  • Smoke testing

3. Smoke test vs. pruebas de regresión

Smoke test

  • Pruebas mínimas que cubren las funcionalidades más importantes/críticas.
  • Se ejecuta con mucha frecuencia y alcance reducido y enfocado.
  • Da una vista rápida de que lo prioritario funciona.
  • Ejemplo (app bancaria): al lanzar una nueva versión, verificar que los usuarios puedan entrar, ver el saldo y hacer transferencias (el "core" del negocio).
  • Ejemplo (Mercado Pago): el core es la transacción/pago; una función agregada (como "Mercado Pago Pro") no sería parte del smoke test porque no es el objetivo principal de la app.
  • Clave: definir cuál es el objetivo principal del negocio/app para saber qué priorizar. Esto depende del contexto (no es lo mismo testear un banco que un supermercado o una app de transporte).
  • También puede incluir lo más crítico en seguridad, aunque no sea la funcionalidad principal (ej: una vulnerabilidad grave).
  • Regla general: el nivel de criticidad determina qué tan a fondo se prueba (un color mal puesto no es tan crítico como una falla de seguridad o de funcionalidad core).

Pruebas de regresión

  • Conjunto de pruebas para verificar que una sección (o todo el sistema) sigue funcionando después de un cambio.
  • Se ejecuta cuando se corrige un bug o se modifica algo, para asegurarse de que no se "rompió" otra parte que antes funcionaba.
  • Alcance más amplio, enfocado en funcionalidades y componentes existentes.
  • Frecuencia variable: depende de cuántos cambios se hagan.

4. Testing estático

  • Se realiza sin ejecutar el sistema.
  • Puede aplicarse a: código, documentación, modelos, diagramas, test cases, test plans, contratos, diseños, etc.
  • Objetivo: encontrar fallas o defectos antes de que el código se ejecute o llegue a producción.

Caja negra vs. caja blanca

  • Ejemplo caja negra: para testear una web, no hace falta saber en qué lenguaje está hecha (PHP, etc.); alcanza con la documentación funcional y la interacción del usuario. (Excepción mencionada: en telefonía, a veces sí hace falta saber detalles técnicos, como qué satélite impacta en qué parte del sistema).
  • Ejemplo caja blanca: al programar el login, se escriben pruebas en código para validar que, por ejemplo, si se pasa un usuario válido devuelva ese usuario, y si se pasa un dato inválido ("manzanas") no devuelva una sesión válida. Se valida que la estructura del código tenga las validaciones correctas.
  • Muchas empresas automatizan gran parte del testing de caja blanca, aunque también existen pruebas manuales de caja blanca.

5. Técnicas de diseño de casos de prueba

5.1 Partición de equivalencias

  • Se dividen los valores de entrada en particiones donde se asume que todo valor de una partición produce el mismo resultado.
  • Si un valor de una partición encuentra un defecto, cualquier otro valor de la misma partición debería encontrar el mismo defecto.
  • Ejemplo: regla "si la edad es menor a 16 no se agrega al padrón". Si falta el "igual" (debería ser "menor o igual"), una persona de 16 años quedaría mal incluida/excluida. Es un error muy común al escribir condiciones lógicas rápido.

5.2 Análisis de valores límite

  • Se testean los valores mínimo y máximo de una partición y su vecino más cercano.
  • Ejemplo genérico: si x debe ser ≤ 10, se testea x=10 y x=11.
  • Ejemplo práctico: formulario que exige ser mayor de 18 años → hay que probar 17, 18 y 19, ya que el error típico es que falte el "o igual" en la condición.

5.3 Tabla de decisiones

  • Verifica la implementación de combinaciones de condiciones y sus resultados.
  • Cada fila = una condición o acción; cada columna = una regla/combinación.
  • Ejemplo: alquiler de auto con dos condiciones ("mayor de 18" y "sin multas previas"). Solo se ofrece el alquiler cuando ambas condiciones son verdaderas.
  • Es similar a las tablas de verdad que se usan en lógica.

5.4 Operaciones CRUD / ABM

  • CRUD: Create, Read, Update, Delete.
  • ABM (en español): Alta, Baja, Modificación (a veces ABMC: + Consulta).
  • Se aplican sobre datos en bases de datos, APIs, interfaces de usuario, etc.
  • Ejemplos:
    • Alta (Create): crear un mail, publicar un posteo, enviar un formulario, cargar un video.
    • Lectura (Read): leer posteos, ver el perfil, visualizar stories/videos.
    • Modificación (Update): actualizar contraseña, cambiar nombre de usuario, editar la descripción de un posteo.
    • Baja (Delete): borrar cuenta, borrar un posteo.
  • Nota: algunos casos son ambiguos según el rol (ej. "cargar un video en YouTube" puede ser Create si lo subís, o Read si solo lo visualizás).
  • Puede haber permisos de solo lectura por motivos de seguridad (un usuario que solo puede consultar, no dar de alta/baja/modificar).

6. Testing basado en la experiencia

Se apoya en la habilidad y experiencia del tester (más experiencia = más eficacia para encontrar errores). Tres técnicas principales:

  1. Error guessing (adivinar dónde puede fallar el sistema).
  2. Testing exploratorio
  3. Checklist-based testing

Testing exploratorio

  • Las pruebas se crean, ejecutan y evalúan simultáneamente, mientras el tester va aprendiendo el sistema.
  • Sirve para explorar en profundidad y crear nuevas pruebas en áreas no testeadas.
  • Suele realizarse en sesiones con tiempo definido, guiadas por un "charter" (objetivos del testing).
  • Puede combinarse con otras técnicas de diseño de pruebas.
  • Ejemplos dados en clase:
    • Videojuegos (ej. Far Cry): mover el personaje por los distintos biomas, interactuar con objetos, vehículos, otros personajes, "romper todo".
    • Jugar a Los Sims probando todas las funciones nuevas de las expansiones.
    • Los speedruns: buscar combinaciones o glitches para romper el juego y completarlo más rápido (ej. Super Mario) — es una forma natural de testing exploratorio hecha por jugadores, no testers.

Pirámide del testing

  • A medida que se sube de nivel, las pruebas tienen más costo y más tiempo.
  • Niveles mencionados (de la base hacia arriba): pruebas unitarias → componentes/business logic → integración/technical features → sistema/conectividad → pruebas funcionales / user testing.
  • Se divide también en pruebas automatizadas y manuales.

7. Ejercicio práctico: escribir test cases

Se trabajó sobre una app de ejemplo ("nuevo contacto") con documentación funcional y no funcional, usando una plantilla de test case en formato vertical (a diferencia del formato horizontal visto antes), con los campos:

  • Título
  • Precondiciones
  • Datos
  • Pasos a seguir
  • Resultado esperado

Recomendaciones clave que surgieron durante la práctica

  • Escribir los test cases en base a la documentación, no a la aplicación, ya que la aplicación puede tener bugs no contemplados en la documentación (eso se prueba en la etapa de ejecución, no de diseño).
  • Ser específico en los pasos: en vez de "ingresar un nombre válido", especificar "ingresar un mail válido" o basarse en las especificaciones concretas (ej. límite de caracteres, campos obligatorios, tipo de datos permitido).
  • No usar caracteres especiales sin control: es una fuente típica de vulnerabilidades (inyección en bases de datos), por lo que validar esto es parte del testing de seguridad.
  • Cada test case debe ser independiente y autocontenido:
    • No asumir que se ejecutó otro test case antes ("no encadenar" casos).
    • Siempre indicar explícitamente la URL/aplicación a usar, aunque parezca obvio.
    • Motivo: distintos testers pueden ejecutar cada caso por separado, y también facilita el trabajo del desarrollador que recibe el reporte de bug (necesita ver el paso a paso completo, no un caso que depende de otro).
    • Excepción razonable: se puede usar una precondición del tipo "el usuario ya existe / ya está logueado" en vez de repetir todos los pasos de creación de usuario, siempre que crear el usuario no sea en sí lo que se está probando.
  • Precondiciones vs. datos:
    • Los datos concretos (nombre, apellido, mail, etc.) van en la sección "Datos".
    • Las precondiciones son los pasos previos necesarios que no forman parte de los pasos de ese test en particular (ej. "existe un contacto creado" si se va a testear la edición de un contacto).
    • "Tener internet" como precondición es válido pero poco usual en la práctica profesional (se da por sentado).
  • No modificar la documentación funcional/técnica original (ni siquiera errores de ortografía), ya que puede romper la trazabilidad de la especificación, sobre todo en metodologías tipo cascada.
  • Realizar una "primera capa" de testing sobre la documentación misma, antes de escribir los test cases: revisar si la información es contradictoria, si falta, si alcanza para cubrir toda la funcionalidad, y pedir que se complete si es necesario.

8. Reflexiones y anécdotas del entorno laboral real

  • La documentación funcional/no funcional no siempre es clara ni completa; a veces sobra información irrelevante y falta la relevante. Hay que aprender a filtrar qué es importante.
  • El nivel de detalle exigido en los test cases depende del líder, del proyecto y del cliente: algunos piden el detalle extremo (para que ningún bug quede oculto bajo un "no aplica" del desarrollador), otros priorizan la velocidad.
  • Los tiempos de testing suelen ser subestimados frente a los de desarrollo, lo que genera fricción, sobre todo hacia el final del proyecto. Recomendación: detectar y reportar los errores más críticos lo antes posible, para dar más margen de reacción.
  • Pueden encontrarse distintas metodologías de trabajo: ágil, cascada, o híbridas.
  • A veces no hay documentación en absoluto y hay que generarla desde cero (caso mencionado de una compañera, Vicky).
  • Ejemplo real de bug de producción: un cliente cargó un mail con caracteres no soportados por el sistema, que no había sido contemplado como caso de prueba — refuerza la importancia de validar caracteres especiales y casos límite en los datos de entrada.
