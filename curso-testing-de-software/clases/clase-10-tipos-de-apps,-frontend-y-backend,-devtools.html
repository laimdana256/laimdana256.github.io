Clase 10 - Tipos de Apps, Frontend y Backend, DevTools

Tipos de aplicaciones

Las aplicaciones pueden desarrollarse de distintas maneras, dependiendo de quién vaya a usarlas y cómo. Como QA, tenemos que tener en cuenta a qué público apunta la aplicación.

Aplicaciones web

Son creadas para utilizarse a través de un navegador (por ej.: Firefox, Safari, Chrome, etc.), no requieren ser instaladas ni actualizadas, y se accede a ellas a través de una URL. Utilizan los bloques estándar para desarrollo web: HTML, CSS y JavaScript. HTML maneja la estructura general de la página y cómo es indexada e interpretada por buscadores, bots o filtros. CSS maneja el diseño, los colores y todo lo relacionado con la accesibilidad. JavaScript maneja toda la parte lógica, lo que hace que una página pueda tener funcionalidad y ser interactiva.

Aplicaciones nativas

Son desarrolladas para un sistema operativo en particular (iOS, Android, Windows, macOS, etc.), diseñadas utilizando sus herramientas y lenguajes de programación específicos, con el fin de aprovechar todas las funcionalidades particulares del sistema operativo y del dispositivo. A diferencia de las apps web, estas solo pueden correr en el sistema para el que fueron diseñadas.

Aplicaciones híbridas

Son aplicaciones construidas utilizando ambas tecnologías (nativa y web). A través de lo que se conoce como un wrapper nativo, pueden mostrar el contenido de una web app, lo que permite que el código sea más fácil de mantener y que se pueda utilizar en distintos dispositivos (ejemplos: Slack, Spotify, Discord).

Cómo funcionan las apps

La mayor parte de las aplicaciones modernas se construyen con el modelo de cliente-servidor, lo cual significa que hay dos partes: el frontend (cliente), con el cual interactúan las personas usuarias, y el backend (servidor), que maneja la lógica, los datos y el almacenamiento.

Estas partes se comunican a través de API (application programming interface), enviando requests y responses.

Frontend

El frontend es lo que ven las personas usuarias: la interfaz de la aplicación. Funciona en el dispositivo o navegador de la persona usuaria, e incluye todo lo relacionado con la pantalla, los botones, los elementos visuales, etc. Es decir, todo aquello con lo que la persona puede interactuar.

Generalmente haremos testeo de frontend, al menos al principio: serán tests funcionales y tests visuales, ya que nos enfocaremos en la necesidad del cliente.

Backend

El backend es donde sucede la lógica del sistema. Generalmente se encuentra en un servidor aparte y se encarga de todas las tareas de procesamiento y lógica, tales como:

  • Validación de datos enviados por el frontend
  • Manejo de autenticación de personas usuarias
  • Mantenimiento de la lógica de las reglas de negocio

Esto último se refiere a que, cualesquiera sean las reglas que maneja el negocio, estas se apliquen en la interacción con el usuario.

Comunicación

La comunicación entre frontend y backend se realiza vía APIs (muchas veces utilizando una arquitectura RESTful), a través de las cuales el frontend (o cliente) envía una request y el backend responde con información en una response.

Developer Tools

Son un conjunto de herramientas incorporadas en los navegadores modernos que nos facilitan hacer debugging (el proceso de identificar y resolver las causas de un bug) y ganar más conocimiento sobre el funcionamiento del frontend y su comunicación con el backend.

Inspector: nos da una vista del HTML de una web y sus estilos (CSS).

Consola: muestra mensajes, advertencias y errores que provengan del JavaScript que corre la aplicación, además de permitir ejecutar pequeños bloques de código. También sirve para ver los métodos de las APIs y detectar qué consultas están fallando.

Network/Red: muestra todas las requests que se realizan, lo cual nos permite ver cómo está funcionando la conexión con el backend, las respuestas que está enviando y su contenido (latencia, tiempo de carga, etc.).

Storage/Almacenamiento: permite inspeccionar todo lo almacenado de manera local, como datos locales, cookies y datos de sesión.

Performance y Network Throttling: herramientas para analizar el rendimiento de nuestra aplicación y también simular distintas condiciones de red.

(Solo en Chrome) Reporte de accesibilidad/Lighthouse Report.

En mobile no hay un equivalente directo de las Dev Tools.

Testing Web

El testing web debe tener en cuenta muchas variables para asegurarse de que nuestra app funcione en distintos navegadores, dispositivos y entornos. Consideraciones a tener en cuenta:

  • Compatibilidad de navegadores
  • Responsive
  • Rendimiento y tiempos de carga
  • Cookies, sesiones, caché
  • Accesibilidad

Testing Mobile

Sumado a las múltiples variables que cubrimos en el testing web, también tenemos que pensar en variables propias de cada dispositivo, interrupciones, etc. Consideraciones a tener en cuenta:

  • Distintos dispositivos, pantallas y sistemas operativos
  • Permisos
  • Interrupciones
  • Condiciones de red
  • Instalación y actualizaciones

Herramientas para Testing Mobile

Emuladores

Ventajas:

  • Bajo costo y fáciles de usar.
  • Rapidez para ejecutar pruebas básicas y automatizadas.
  • Disponibilidad inmediata, a menudo integrados en Android Studio.

Desventajas:

  • No siempre replican con precisión el rendimiento o las características de hardware de un dispositivo real.
  • Puede haber discrepancias en la experiencia de usuario o en la ejecución de ciertas funciones.

Granja de dispositivos

Ventajas:

  • Ofrecen un nivel de confiabilidad y precisión mucho mayor al probar en hardware real.
  • Permiten probar en una gran variedad de modelos, versiones de sistema operativo y tamaños de pantalla, incluyendo dispositivos plegables o tablets.
  • Excelentes para la validación de rendimiento y escenarios de uso en el mundo real.

Desventajas:

  • Generalmente implican un costo mayor y requieren más mantenimiento que los emuladores.
  • Pueden ser más lentos en la configuración inicial y en la ejecución de pruebas.

Apartado regla de negocio

Entender la regla de negocio nos va a ayudar a tomar decisiones. Es posible que algunos de los bugs que encontremos sean, en realidad, condiciones impuestas por la empresa y/o el negocio con el que estemos trabajando. Por ejemplo, por cuestiones de accesibilidad se piden ciertos contrastes de colores; si no se cumplen según la especificación, no podemos aprobar el testing, tanto por usabilidad como por cuestiones de identidad de marca.

Accesibilidad: para los lectores de pantalla se utilizan determinados tipos de etiquetas, de modo que estos puedan identificar a dónde saltar y así una persona con baja capacidad visual pueda navegar con facilidad por la aplicación. Todo esto siempre estará aclarado en los requerimientos del producto. Por más que haya cosas que no coincidan con nuestro criterio, si es lo que quiere el cliente, hay que saber respetar lo que pide / la bajada de línea sobre cómo cumplir ciertos criterios de accesibilidad.
