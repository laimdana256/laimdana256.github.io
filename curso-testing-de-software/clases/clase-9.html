Hacemos un repaso sobre el test plan:

describe la estrategia con la que vamos a probar el producto. se escribe al inicio de un proyecto. no es algo que se escriba a la par de los test cases sino cuando apenas arranca. Establece las estrategias de prueba. Genrealmente escrito por el QA de mayor experiencia. Usamos el ejemplo de test plan provisto en la bibliografía de drive del curso [Buscar ejemplos de Test Plan en internet] Es solamente planifiacion super previa a cualquier prueba o testeo. en esta instancia ain no existen test plans.

Podemos el ISTQB como referencia de documentación (Los exámenes son pagos pero la bibliografía es gratuita). También está el formato IEEE829 como referencia.

Un test plan es un documento que describe que es lo que va a tranajar qa durante todo el proyecto e incluye los siguientes datos:

Objetivos Se sientan onjetivos del proceso de testing (Cuál es el propósito de tener un proceso de testing en este caso?):

  • Verificar que las funcionalidades implemetndas cumplen los requisitos
  • Detectar defectos antes de la publicación
  • Reducir el riesgo de errores en producción
  • Validar los flujos críticos del negocio

Alcance (Scope) Todo lo que entra dentro de la esfera de testing. Se especifican qué se incluye dentro del testing y qué cosas NO se van a testear dentro del proyecto (en este momento y en este contexto y en esta versión de la aplicación). Las cosas que quedan por fuera de la esfera de QA ERP = Sistema que centraliza varias aplicaciones.

Estrategia de testing Puede ser algo tan sencillo como listar los tipos de testing que se van a hacer. los mas generales son smoke, functional, regression, exploratory cada una de las acciones del test plan. la estrategias de testing responde a qué voy a testear, cómo lo voy a hacer.

PReguntas para hacer: Las cosas a testear y las que no se testean, es establecido por quien? si no hay ninguna especificacion, el tester tiene que asumir que se va a testear todo lo posible?

Se ve que funcionalidades se van a probar y cuáles no van a ser probadas.

Ambiente de Testing = Dónde vamos a testear. URL, Base de datos, qué navegadores, qué dispositivos,

Criterios de entrada y criterios de salida responden a la pregunrta qué necesito para arrncar a testear? por ejemplo: los resquisitos estén aprobados el desarrollo ya esté finalizado. el ambiente QA está disponooble Se haya realiazdo el deployment (se mandó desde donde se programa al código a donde se hace el QA) Que QA tenga acceso a la aplicacion Los criterios de salida dicen cómo aprobar como QA cualquiera de las funcionalidades que estoy testeando.

Riesgos ambiente QA inestable - impacto alto Retrasos en desarrollo - medio datos de prueba incorrectos - medio cambios de alcance durante el sprint - alto

Mitigaciones (cómo planeamos mitigar los riesgos)

  • mantener una comunicación diaria con Desarrollo
  • Tener datos de prueba preparados previamente
  • validar el ambiente antes de empezar las pruebas
  • ejecutar un smoke testing después de cada deployment

Roles y responsabilidadaes

Herramientas ejemplos

  • Jira (gestión de bugs)
  • TestRail (casos de prueba)
  • Chrome DevTools
  • Postman (pruebas de API)
  • Slack (comunicación)

Cronograma Especificamos cuánto creemos que es lo que nos va a llevar cada una de las tareas listadas más arriba.

Entregables Qué es lo que va a producir el equipo de QA. Los documentos que va a estar entregando QA durante el proyecto

  • test plan
  • test cases
  • reporte de bugs
  • reporte de ejecución
  • reporte final de testing
  • recomendación de release (Go / No Go) Aprobaciones Rol - Nombre - Estado (pendiente / aprobado)
